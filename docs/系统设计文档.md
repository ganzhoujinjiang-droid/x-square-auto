## 1. 项目定位

部署在 Linux 服务器上的**个人内容自动分发系统**。

```text
你在 X 发布原创帖子
        ↓
X 官方 API（GET /2/users/{id}/tweets + since_id）
        ↓
X Monitor 发现新帖子
        ↓
PostgreSQL 保存原始内容（唯一索引去重）
        ↓
规则过滤（帖子类型 / 关键词 / 排除词）
        ↓
内容处理（原样 / 模板化 / AI 改写，V1 默认前两者）
        ↓
图片处理（下载 → 预签名上传 → 轮询状态）
        ↓
Binance Square OpenAPI（content/add）
        ↓
自动发布
```

**目标**：你只负责发 X，服务器自动把符合规则的内容同步到 Binance Square。

系统提供 Web 后台，管理账号、规则、任务、日志、API 消耗和发布状态。

### 1.1 单向性声明

本系统是**只读 X、只写 Binance** 的单向管道：

- 对 X：只调用读取类接口，**永不调用** `POST /2/tweets`、删除、点赞、关注等写入接口。
- 对 Binance Square：只调用发布类接口，**永不**编辑或删除已发布内容（OpenAPI 本身也不支持，见 §11.4）。

这条声明同时是安全边界和成本边界：它保证系统不会产生 X 侧的写入费用（$0.015～$0.200/请求）。

## 2. 第一原则：只使用 X 官方 API

第一版**禁止**在生产系统中使用：

```text
Playwright / Selenium / Puppeteer
Chrome 或任何无头浏览器自动化
X 网页 DOM 抓取
第三方 X 爬虫或代理 API
```

X 侧只通过官方 API 获取数据。理由：

1. 不依赖 X 网页 DOM，页面改版不会直接击穿监控器。
2. 不需要服务器长期维持 X 网页登录态（Cookie 易失效且违反 ToS 风险高）。
3. 官方 API 的错误码、限流头、认证刷新机制都是可程序化处理的。
4. 成本可计量、可设上限（Spending Limit）。
5. 适合长期无人值守运行。

> **开源提示**：README 中需明确声明本项目不使用任何爬虫手段，避免被误认为绕过平台限制的工具。

## 6. X Monitor 设计

### 6.1 接口与参数

唯一数据源：

```http
GET /2/users/{id}/tweets
```

必需查询参数：

```text
since_id            只返回 ID 大于此值的帖子（核心去重手段）
max_results         5～100，V1 固定 100
expansions            attachments.media_keys,referenced_tweets.id,author_id,edit_history_tweet_ids
tweet.fields          id,text,created_at,author_id,conversation_id,attachments,
                      entities,referenced_tweets,edit_history_tweet_ids,
                      reply_settings,lang,possibly_sensitive
media.fields          media_key,type,url,preview_image_url,width,height,alt_text,duration_ms
user.fields           id,username
pagination_token      分页（仅回溯导入时使用）
```

### 6.2 轮询周期

默认 **30 秒**，后台可配置：

```text
15 / 30 / 60 / 120 / 300 秒
```

**为什么是 30 秒而不是更快**：

- X 对 endpoint 存在 App 级与 User 级 rate limit，高频轮询会撞 429 并触发退避，反而更慢。
- 计费按「响应返回的资源数」，空响应不产生资源（见 §18），所以频率本身不直接烧钱，但会消耗 rate limit 配额。
- 30 秒对内容分发场景已接近实时，人眼无法区分 15 秒与 30 秒的差别。

**禁止**：写死无限循环请求。必须读取响应头 `x-rate-limit-remaining` / `x-rate-limit-reset`，低于阈值时主动休眠至 reset 时间。

### 6.3 账号级持久化状态

`x_accounts` 表保存：

```text
last_tweet_id             已成功处理的最大 Tweet ID（Snowflake）
last_successful_poll_at   最后一次成功轮询时间（UTC）
last_poll_status          OK / RATE_LIMITED / AUTH_FAILED / NETWORK_ERROR / SERVER_ERROR
consecutive_failures      连续失败次数（用于告警与自动暂停）
```

### 6.4 单次轮询流程

```text
Worker tick
 ↓
SELECT ... FROM x_accounts WHERE status = 'ACTIVE'
 ↓
对每个账号加 Redis 分布式锁（防止多实例重复轮询）
 ↓
读取 last_tweet_id
 ↓
GET /2/users/{id}/tweets?since_id={last_tweet_id}
 ↓
响应 Zod 校验
 ↓
按 created_at 升序排序（旧→新，保证发布顺序）
 ↓
逐条：
   INSERT INTO x_posts ... ON CONFLICT (x_post_id) DO NOTHING
   ↓ 若插入成功（非重复）
   创建 sync_job（status = DISCOVERED）
   ↓ 入队 sync-post
   更新 last_tweet_id = max(id)
 ↓
更新 last_successful_poll_at / last_poll_status
```

**关键约束**：

- `last_tweet_id` 的推进必须在**同一事务**内与该批帖子的写入一起提交，否则崩溃时会造成帖子丢失或重复。
- Tweet ID 是 Snowflake（时间有序递增），可直接用字符串比较转 bigint 比较，不能按数组顺序取最后一个。

### 6.5 首次连接：baseline 机制（关键）

**绝对不能**在首次授权后把历史几千条帖子全部同步到 Binance。

```text
用户点击「连接 X」
 ↓
OAuth 授权 → 拿到 token → GET /2/users/me → 记录 x_user_id
 ↓
调用 GET /2/users/{id}/tweets?max_results=5（不带 since_id）
 ↓
取返回结果中最大的 Tweet ID
 ↓
写入 last_tweet_id 作为 baseline
 ↓
status = ACTIVE，开始监控
```

语义：**只同步「用户连接系统之后」发布的新帖子。**

后台提供可选的历史导入按钮（默认不执行）：

```text
[导入最近 10 条]
[导入最近 50 条]
```

导入时必须逐条经过与自动同步**完全相同**的规则过滤，且必须在 UI 上二次确认。

### 6.6 服务器重启恢复

```text
进程启动
 ↓
读取 PostgreSQL 中的 last_tweet_id
 ↓
以该 ID 作为 since_id 查询 X
 ↓
获取中断期间产生的全部新帖子（必要时分页）
 ↓
逐条写入并推进
```

**保证：服务器重启不丢帖子。** 前提是 `last_tweet_id` 只在帖子成功入库后才推进（§6.4）。

若中断时间过长导致新帖超过单页上限，需循环使用 `pagination_token` 直到取完，再恢复定时轮询。

## 7. X OAuth 与 Token 安全

### 7.1 授权流程

```text
OAuth 2.0 Authorization Code + PKCE

后台点击「连接 X」
 ↓
生成 state（32 字节随机，存 Redis，TTL 10 分钟）
 ↓
生成 code_verifier（43～128 字符随机）→ code_challenge = BASE64URL(SHA256(verifier))
 ↓
302 跳转 X 授权页
 ↓
用户授权
 ↓
X 回调 /api/x/oauth/callback?code=...&state=...
 ↓
校验 state（一次性，用后即删）
 ↓
POST /2/oauth2/token（grant_type=authorization_code + code_verifier）
 ↓
拿到 access_token / refresh_token / expires_in
 ↓
GET /2/users/me → 记录 x_user_id、username
 ↓
Token 加密后入库，执行 baseline（§6.5）
```

### 7.2 所需 scope

**必需**：

```text
tweet.read          读取帖子
users.read          读取用户信息（/2/users/me）
offline.access      获取 refresh_token，长期运行必需
```

**明确不申请**：

```text
tweet.write         不需要，本系统不写 X
like.write
follows.write
dm.write
```

最小权限原则。开源用户复用时也应只申请这三项——这既降低审核难度，也让用户放心。

### 7.3 App 与账号的关系（Owned Reads 前提）

要享受 $0.001/资源 的 Owned Reads 定价，必须满足：

```text
认证用户（access_token 的所有者）
        =
Developer App 的 Owner
        =
被监控的 X 账号
```

因此 V1 定位是：**一个 X 账号 → 该账号自己的 Developer App**。

若用 A 的 App 去读 B 的时间线，`{id}` 不匹配认证用户，将按标准价 **$0.005/资源** 计费（5 倍）。这一点必须在 README 和后台 UI 中显著提示。

### 7.4 Token 静态加密

数据库中**禁止**明文存储：

```text
access_token
refresh_token
client_secret
Binance OpenAPI Key
TOTP Secret
```

统一使用 **AES-256-GCM**：

```text
密文格式：base64( iv(12B) || ciphertext || authTag(16B) )
密钥来源：环境变量 APP_ENCRYPTION_KEY（32 字节，base64 编码）
字段命名：access_token_encrypted / refresh_token_encrypted / api_key_encrypted
```

GCM 提供认证加密，密文被篡改时解密直接抛错，避免使用被改写的 Token 发起请求。

服务器环境变量：

```text
APP_ENCRYPTION_KEY      # 32 字节 base64，缺失时进程拒绝启动
X_CLIENT_ID
X_CLIENT_SECRET
DATABASE_URL
REDIS_URL
SESSION_SECRET
```

### 7.5 Token 刷新

```text
access_token 过期前 5 分钟主动刷新
刷新失败 → 退避重试 3 次（60s / 300s / 900s）
仍失败 → x_accounts.status = TOKEN_EXPIRED，停止轮询，后台红字告警 + 提示「重新授权」
```

刷新后新旧 refresh_token 都要正确处理：X 的 refresh_token 是一次性的，**必须在同一事务内**用新值覆盖旧值，否则并发刷新会导致 Token 失效。

### 7.6 日志红线

任何级别的日志都**禁止**输出：

```text
X access_token / refresh_token / client_secret
Binance OpenAPI Key
Cookie / Set-Cookie
Session ID
APP_ENCRYPTION_KEY
Authorization 请求头
```

实现方式：Pino 配置 `redact` 路径列表 + 自定义序列化器；HTTP 客户端在记录请求前统一脱敏。CI 中增加一条 grep 检查，防止回归。

## 8. X 数据模型

### 8.1 帖子类型判定

依据 API 返回字段判定：

```text
referenced_tweets 为空或不存在        → ORIGINAL（原创）
referenced_tweets[].type = "replied_to"  → REPLY
referenced_tweets[].type = "retweeted"   → REPOST
referenced_tweets[].type = "quoted"      → QUOTE
attachments.media_keys 中存在 type = "photo" → 含图片
attachments.media_keys 中存在 type = "video" / "animated_gif" → 含视频（V1 不同步）
```

### 8.2 V1 同步策略

| 类型 | 默认行为 | 可配置 |
|---|---|---|
| 原创纯文本 | ✅ 自动同步 | 是 |
| 原创 + 图片 | ✅ 自动同步 | 是 |
| Quote（引用） | ❌ 不同步 | 是 |
| Reply（回复） | ❌ 不同步 | 是（不建议开） |
| Repost（转推） | ❌ 不同步 | 是（不建议开） |
| 含视频 / GIF | ❌ 不同步 | V1 不开放 |

理由：Reply 脱离上下文后在 Square 上语义不完整；Repost 是他人内容，存在版权问题；Quote 需保留被引用帖上下文，V1 文本模板尚不支持。

## 9. 同步任务状态机

### 9.1 状态定义

```text
DISCOVERED      已从 X 发现并入库，尚未评估规则
    ↓
FILTERED        规则判定为「不同步」（终态，非错误）
    ↓
QUEUED          通过规则，已入队等待处理
    ↓
PROCESSING      内容处理中（文本模板 / AI 改写）
    ↓
MEDIA_PROCESSING 图片下载与上传中
    ↓
PUBLISHING      已调用 content/add，等待响应   ← 危险区
    ↓
SUCCESS         Binance 返回明确成功 + post_id

异常分支：
FAILED          明确失败，不可自动重试（终态，等待人工）
UNCERTAIN       发布结果未知（终态，等待人工确认）
CANCELLED       人工取消（终态）
```

### 9.2 状态转移约束

- 只允许沿上述方向转移，任何非法转移在代码层面抛错（用 TypeScript 联合类型 + 运行时校验双保险）。
- `SUCCESS` / `FAILED` / `UNCERTAIN` / `CANCELLED` / `FILTERED` 是**终态**，Worker 不得自动改变。
- 唯一的人工出口：`UNCERTAIN` → 用户在后台点击「确认未发布并允许重试」→ 回到 `QUEUED`；或点击「确认已发布」→ 转为 `SUCCESS`（需人工补录 post_id）。

### 9.3 为什么必须有 UNCERTAIN

```text
Worker
 ↓
调用 content/add
 ↓
请求已发出
 ↓
网络超时 / 504 / 连接中断
 ↓
服务器不知道 Binance 到底发布了没有
```

此时**绝对不能自动重试**，否则可能造成同一内容重复发布：

```text
帖子 1
帖子 2      ← 重复内容，影响账号质量
```

因此：

```text
PUBLISHING --(超时/504/中断)--> UNCERTAIN
```

后台显示：

```text
⚠ 发布结果未知
可能已经发布成功。

[打开 Binance Square 核对]
[确认未发布 → 允许重试]
[确认已发布 → 标记成功]
```

**外部依据（本次核实）**：Binance 官方 square-post skill 文档明确写道——若脚本输出 `Success!` 但 `ID: unavailable`，说明 `/content/add` 在提交后返回了 504，此时**视为发布成功**，只是拿不到帖子 ID 和链接。

> **设计决策记录**：官方 skill 把 504 当作「成功」，本系统选择更保守的 `UNCERTAIN`。
> 理由：官方 skill 是**人在环**的交互式场景，用户能立刻看到 Square 上有没有新帖；本系统是**无人值守**的自动管道，一旦误判为失败并重试，就会产生重复内容且无人察觉。宁可偶尔多一次人工确认，不可自动制造重复发布。
> 同时本系统保留官方语义作为参考：若用户在后台选择「确认已发布」，则按官方 skill 的逻辑标记 `SUCCESS` 且允许 `post_id` 为空。

### 9.4 幂等键

每个 `sync_job` 携带幂等键：

```text
idempotency_key = sha256(x_post_id + binance_account_id + content_hash)
```

发布前先查该键：若已存在 `SUCCESS` 记录，直接跳过。这是防止 UNCERTAIN 人工重试造成重复的第二道防线。

## 10. 队列与重试

### 10.1 队列划分（BullMQ）

```text
sync-post           规则过滤 + 内容处理入口
process-content     文本模板 / AI 改写
download-media      从 X CDN 下载图片
upload-media        预签名上传 + 轮询处理状态
publish-binance     调用 content/add
reconcile-uncertain UNCERTAIN 任务的定期核对（V2）
```

队列参数：

```text
attempts            5
backoff             { type: 'custom' }  → 30s / 60s / 120s / 300s / 600s
lockDuration        60_000（publish-binance 设为 120_000）
stalledInterval     30_000
removeOnComplete    { count: 1000 }
removeOnFail        false          ← 失败任务必须保留供排查
```

### 10.2 错误分类

**可重试**（自动退避）：

```text
HTTP 429                        读取 Retry-After / x-rate-limit-reset，休眠至该时刻
HTTP 500 / 502 / 503            指数退避
网络超时（连接/读取）             指数退避
DNS 暂时失败（EAI_AGAIN）        指数退避
ECONNRESET / EPIPE              指数退避
```

**不可重试**（直接 `FAILED`，等待人工）：

```text
HTTP 401 / 403                  Token 或 API Key 失效
Binance 220003 / 220004         密钥不存在 / 已过期
Binance 220009                  日发帖限额（100/日）已用尽
Binance 220014                  日上传限额（400/日）已用尽
Binance 20002 / 20022           敏感词命中
Binance 20013                   内容长度超限
Binance 20020 / 220011          内容为空
Binance 30008 / 2000001 / 2000002  账号或设备发帖受限
Zod 校验失败                     响应结构不符预期（可能是接口变更，需人工介入）
```

**特殊：504 与超时 → `UNCERTAIN`，不进入重试队列**（§9.3）。

### 10.3 429 处理细节

```text
收到 429
 ↓
读取响应头：
   x-rate-limit-remaining
   x-rate-limit-reset（Unix 秒）
   Retry-After（若存在，优先）
 ↓
计算休眠时长 = max(reset - now, Retry-After, 1s)
 ↓
将账号 poll 状态置为 RATE_LIMITED
 ↓
休眠到期后恢复
 ↓
连续 3 次 429 → 自动将该账号轮询间隔翻倍（最高 300s）并在后台告警
```

### 10.4 Worker 崩溃恢复

- BullMQ 的 `lockDuration` + `stalledInterval` 保证 Worker 崩溃后任务被重新分配，不会消失。
- 但若崩溃发生在 `PUBLISHING` 阶段且请求已发出，重新分配的任务**必须先检查数据库状态**：若已是 `UNCERTAIN` 或 `SUCCESS`，立即终止，不得重复调用 Binance。
- 因此 `publish-binance` 处理器第一步永远是「读取并校验当前 job 状态」，而非直接发请求。

## 11. Binance Square 模块

### 11.1 接口规格（已从官方源码逐行核实）

来源：`github.com/binance/binance-skills-hub` → `skills/binance/square-post/scripts/lib.mjs`

**Base URL（注意两个版本并存，不可混用）**：

```text
V1  https://www.binance.com/bapi/composite/v1/public/pgc/openApi
    └── 仅用于 POST /content/add（发布）

V2  https://www.binance.com/bapi/composite/v2/public/pgc/openApi
    └── 用于 POST /image/presignedUrl 与 POST /image/imageStatus
```

> ⚠️ 这是最容易踩的坑：**发布走 V1，图片走 V2**。全部用 V2 会导致 `/content/add` 失败。

**统一请求头**（三个接口全部相同）：

```http
X-Square-OpenAPI-Key: <你的密钥>
Content-Type: application/json
clienttype: binanceSkill
```

所有接口均为 **POST**，参数放在 JSON body（不是 query，不是 form）。

**成功判定**：响应体 `code === "000000"`（**字符串**，不是数字 0），业务数据在 `data` 字段。

```json
{ "code": "000000", "message": "...", "data": { ... } }
```

**端点一：获取预签名上传地址**

```http
POST {V2}/image/presignedUrl
{ "imageName": "chart1.png" }

→ data: { "presignedUrl": "https://...", "fileTicket": "..." }
```

随后对 `presignedUrl` 执行 **PUT**，body 为图片二进制，头 `Content-Type` 按扩展名映射：

```text
jpg/jpeg → image/jpeg     png → image/png      gif → image/gif
webp → image/webp         mp4 → video/mp4      mov → video/quicktime
avi → x-msvideo           webm → video/webp    其他 → application/octet-stream
```

PUT 失败（非 2xx）即上传失败。注意这一步**不带** `X-Square-OpenAPI-Key`，凭据已包含在预签名 URL 中。

**端点二：轮询图片处理状态**

```http
POST {V2}/image/imageStatus
{ "fileTicket": "..." }

→ data: { "status": 0|1|2, "imageUrl": "...", "failedReason": "..." }
```

```text
status = 1   处理完成，imageUrl 可用     → 返回
status = 2   处理失败                   → 抛错，携带 failedReason
其他（如 0） 处理中                      → 继续轮询
```

官方轮询参数：**间隔 3000 ms，最多 10 次**（即最长 30 秒）。本系统沿用该参数，超时按可重试错误处理。

**端点三：发布内容**

```http
POST {V1}/content/add
```

短帖（`contentType = 1`）：

```json
{
  "contentType": 1,
  "bodyTextOnly": "正文内容 $BTC #crypto",
  "imageList": ["https://...imageUrl1", "https://...imageUrl2"]
}
```

长文章（`contentType = 2`）：

```json
{
  "contentType": 2,
  "bodyTextOnly": "文章正文...",
  "title": "Market Report",
  "cover": "https://...imageUrl"
}
```

```text
→ data: { "id": "<帖子ID>", "shareLink": "<分享链接>" }
```

**字段名要点**：正文字段是 **`bodyTextOnly`**（不是 `content` / `text`）；图片列表是 **`imageList`**；封面是 **`cover`**（单个 URL 字符串，不是数组）。

**504 特殊处理**：官方脚本对 `/content/add` 的 504 做了显式特判，返回 `publishStatus: "success_without_post_id"`，即**视为已发布成功但拿不到 ID**。本系统的处理见 §9.3。

### 11.2 接口能力矩阵

Binance Square OpenAPI 提供独立的发帖密钥，**与资产、交易接口完全隔离**，泄露不会危及资金。

支持的发布形态：

| contentType | 形态 | 媒体 | 说明 |
|---|---|---|---|
| `1` | 短帖 | `imageList`，**最多 4 张** | 文字或图文短帖 |
| `2` | 长文章 | `cover`，**恰好 1 张** | 需 `title`，封面图单张 |
| — | 视频帖 | 1 个视频 + 自动首帧封面 | 需 ffmpeg，**V1 不做** |

**约束**：

- 图片与视频**互斥**，同一帖不能同时带。
- 文章模式（有 `title`）不能传 `imageList`，只能传单张 `cover`。
- 图片流程：预签名上传 → 轮询处理状态 → 拿到最终 `imageUrl` → 才能 `content/add`。
- 正文中的 `$BTC`（cashtag）与 `#topic`（hashtag）由 Binance **服务端解析**，客户端原样传递即可，不要自行转义或改写。

### 11.3 硬限额（必须在代码中前置校验）

```text
100 帖 / 日       发布次数上限
400 上传 / 日     媒体上传次数上限
```

实现要求：

- Redis 计数器按 **UTC 日**滚动，键名 `binance:{accountId}:post_count:{yyyymmdd}`，TTL 48h。
- 发帖前检查：若已达 95（预警）在后台黄色提示；达 100 直接拒绝入队并标记 `FAILED`（错误码 `DAILY_POST_LIMIT`），**不要**发出去等 220009。
- 上传同理，阈值 380 / 400。
- 注意：图片上传失败也计入 400 配额，因此 `download-media` 阶段失败**不应**触发 `upload-media` 重试超过 2 次。

### 11.4 错误码映射表

| Binance code | 含义 | 系统状态 | 是否重试 | 用户可见提示 |
|---|---|---|---|---|
| `220003` | API Key 不存在 | `FAILED` | 否 | 密钥无效，请重新填写 |
| `220004` | API Key 已过期 | `FAILED` | 否 | 密钥已过期，请到创作者中心重新生成 |
| `220009` | 日发帖限额 | `FAILED` | 否 | 今日 100 帖已达上限，UTC 0 点后自动恢复 |
| `220014` | 日上传限额 | `FAILED` | 否 | 今日 400 次上传已达上限 |
| `20002` / `20022` | 敏感词 | `FAILED` | 否 | 内容命中平台敏感词，需人工修改 |
| `20013` | 内容长度受限 | `FAILED` | 否 | 正文超长，需截断或人工处理 |
| `20020` / `220011` | 内容为空 | `FAILED` | 否 | 处理后正文为空，检查过滤规则 |
| `30008` / `2000001` / `2000002` | 账号或设备发帖受限 | `FAILED` | 否 | 账号被平台限制，请联系 Binance |
| HTTP 504 / 超时 | 结果未知 | `UNCERTAIN` | 否 | ⚠ 发布结果未知，请核对后确认 |
| HTTP 5xx（非 504） | 服务端错误 | 保持原状态 | 是 | 自动重试中 |
| HTTP 429 | 限流 | 保持原状态 | 是 | 自动退避中 |

> **注意**：错误码可能随平台演进新增。**任何未在表中的错误码一律按 `FAILED` + 不重试处理**，并记录原始 code/message 供人工判断，绝不乐观地当作可重试。

### 11.5 明确不支持的操作

OpenAPI **不提供**以下能力（本次核实官方 skill 文档）：

```text
读取 / 列出 / 搜索已发布的 Square 帖子
编辑已发布帖子
删除已发布帖子
评论、点赞等互动
用户资料或账号管理
定时发布 / 草稿箱
```

这直接决定了 v1 文档中两条设计的正确性，本版将其从「V1 不做」升级为「**平台不支持，V1/V2 均无法做**」：

- §13 X 编辑后不能自动同步修改 Binance 帖子。
- §14 X 删帖后不能自动删除 Binance 帖子。

后台 UI 需明确告知用户这一限制，避免误期待。

### 11.6 密钥安全

```text
存储      AES-256-GCM 加密后入库（api_key_encrypted）
显示      仅掩码：前 5 位 + ... + 后 4 位，例如 abc12...xyz9
传参      只通过环境变量或加密配置文件，禁止作为命令行参数
          （CLI 参数会出现在 ps 输出与 shell history 中）
日志      任何级别都不打印，Pino redact 覆盖
接口      后台 API 永不返回完整密钥，修改时只接受新值、不回显旧值
```

密钥获取路径（写入 README）：

```text
https://www.binance.com/square/creator-center/home
→ AI Skills / API Management → 生成 Publishing API Key
```

## 12. 图片处理流程

```text
X API 返回 attachments.media_keys
 ↓
展开 media.fields 拿到 url（photo 类型为直链）
 ↓
download-media：服务器下载到临时目录（限制大小 ≤ 15MB，超时 30s）
 ↓
校验：MIME 白名单（jpeg/png/webp）、尺寸、非空
 ↓
upload-media：请求 Binance 预签名 URL → PUT 上传
 ↓
轮询图片处理状态（间隔 2s，最多 30 次 = 60s）
 ↓
拿到最终 imageUrl
 ↓
publish-binance：content/add，imageList 按原顺序传入
```

**失败降级**：

```text
单张图片下载/上传失败
 ↓
重试最多 2 次（受 400/日 上传限额约束，见 §11.2）
 ↓
仍失败 → 后台标记该任务为「图片处理失败」
 ↓
用户可选择：
   [仅发布文字]     → 去掉 imageList 重新入队
   [放弃该帖]       → CANCELLED
   [手动重试]       → 重新入队
```

**不允许**自动降级为纯文字发布——图片缺失会改变内容语义，必须人工确认。

**临时文件**：下载目录使用容器内 `/tmp/x-square-media`，任务结束（成功或失败）后立即删除；进程启动时清空残留。禁止把媒体文件长期留在磁盘。

## 13. X 编辑与删除

### 13.1 编辑

```text
10:00  X 发帖        → 系统同步 → Binance 发布成功
10:05  X 编辑该帖
```

V1 处理：

```text
轮询时比对 edit_history_tweet_ids 与已存记录
```

## 14. 文本处理

### 14.1 三种模式

后台单选：

```text
○ 原样          X 正文完全不变
○ 模板化        按用户自定义模板包装
○ AI 改写       V1 默认关闭，见 §15
```

### 14.2 原样模式

```text
X text  →  Binance content（逐字节不变）
```

注意：`$BTC` 与 `#topic` 原样传递，Binance 服务端会自行解析成 cashtag/hashtag。**不要**做任何转义。

### 14.3 模板化模式

用户可配置模板，支持变量：

```text
{text}              X 正文
{url}               X 原帖链接
{username}          X 用户名
{date}              发布日期（按设置时区）
{hashtags}          固定标签串
```

默认模板：

```text
{text}

—
来源：@{username}
{url}
```

**长度校验**：Binance 对正文长度有限制（错误码 `20013`，具体上限官方未公开数值）。实现策略：

- 模板渲染后先按 **280 字符**做软性预警（后台黄字提示）。
- 实际超限由 `20013` 兜底，映射为 `FAILED` + 明确提示「正文超长」。
- ⚠️ **待验证**：Square 正文的准确字符上限需用户在真实环境试发一条长文确认，确认后写入配置常量。

### 14.4 X 链接与成本的关系

模板中的 `{url}` 是指向 x.com 的链接，发布到 **Binance**，**不经过 X API**，因此**不产生** X 的 `Post: Create (with URL)` = $0.200 费用。

但若将来（V2+）增加「回写 X」功能，必须重新评估该项成本——$0.200/次 是 $0.015 的 13 倍。

```typescript
interface AIProvider {
```

部署目标为 Oracle Cloud Always Free ARM 实例，实测约束：

```text
架构        aarch64 / ARM64（2 核 Neoverse-N1，无超线程）
内存        11.65 GB，无 swap
磁盘        125 GB
宿主机      未安装 node / npm / go / java / gcc / make
已占用端口  443（Xray 独占）、23888（Clash 订阅）、2368（Ghost，仅 127.0.0.1）
已有服务    Ghost 6.x + MySQL 8.0、Xray、Clash、site-worker（3 个 systemd 定时器）
```

**三条硬约束**：

1. **ARM64 镜像可用性**：所有基础镜像必须有 `linux/arm64` 变体。`node:22-slim`、`postgres:16`、`redis:7`、`caddy:2` 均官方支持 ARM64；需编译的原生依赖（如 `argon2`）必须在容器内针对 arm64 构建，不能依赖宿主机工具链。
2. **2 核 CPU 上限**：`next build` 与 `prisma generate` 是 CPU 密集操作，必须在**构建阶段**完成，运行时容器只做 `next start`。禁止在服务器上跑 watch 模式。
3. **443 端口冲突**：见 §16.3。

### 16.2 Docker Compose 服务

```yaml
services:
  caddy        # 反向代理 + TLS（端口见 §16.3）
  web          # Next.js，仅内网
  api          # Fastify，仅内网
  worker       # 全部 worker 单进程，仅内网
  postgres     # 16，仅 Docker 内网
  redis        # 7，仅 Docker 内网
```

**网络隔离（强制）**：

```text
postgres  5432   不映射到宿主机，只在 compose 内部网络可达
redis     6379   不映射到宿主机，只在 compose 内部网络可达
web       3000   不映射到宿主机，仅 caddy 可达
api       4000   不映射到宿主机，仅 caddy 与 web 可达
```

`docker-compose.yml` 中这些服务**不写 `ports:`**，只用 `expose:`。任何情况下都不能出现：

```text
5432 → Internet
6379 → Internet
```

数据卷：

```text
postgres_data   → /var/lib/postgresql/data
redis_data      → /data（开启 AOF）
media_tmp       → /tmp/x-square-media（可丢弃，无需备份）
caddy_data      → /data（TLS 证书）
```

备份：`pg_dump` 每日一次，复用服务器上已有的 site-worker 备份定时器机制，产物落 `/var/lib/site-worker/backups/`（该目录已存在且已纳入现有备份流程）。

### 16.3 443 端口冲突解决方案

宿主机 443 已被 Xray 独占，Caddy **不能**直接绑定 443。三种方案，按推荐度排序：

**方案 A（推荐）：Caddy 监听高位端口 + 现有 Nginx 按 server_name 分流**

```text
Caddy 监听 127.0.0.1:8443（HTTP，不启用自身 TLS）
宿主机 Nginx 443 增加一个 server 块：
    server_name  square.yourdomain.com
    → proxy_pass http://127.0.0.1:8443
TLS 证书由 Nginx/Cloudflare 侧统一管理
```

优点：与现有 Ghost（`aidukey.uk` 走 Cloudflare + Nginx 反代）架构一致，不新增对外端口，不触碰 Xray。

**方案 B：子域名 + Cloudflare 代理，Caddy 监听 8443**

```text
Cloudflare DNS：square.yourdomain.com → 服务器 IP（橙色云开启）
Cloudflare SSL 模式：Full (strict)
Cloudflare Origin Certificate 或让 Caddy 用 DNS-01 challenge 申请证书
Caddy 监听 8443，Cloudflare 回源到 8443
```

优点：完全不动宿主机 Nginx。缺点：需在 Cloudflare 配置回源端口，且需放行 8443 入站。

**方案 C（仅调试）：Caddy 只监听 127.0.0.1 + SSH 隧道**

```text
Caddy 监听 127.0.0.1:8080
本地通过 ssh -L 8080:127.0.0.1:8080 访问后台
```

优点：零暴露，最安全。缺点：只能本人访问，不适合长期运行告警查看。**开发阶段推荐此方案。**

> ⚠️ **不要**尝试停止 Xray 来腾出 443——它是服务器上已在运行的既有服务，停止会造成用户现有网络配置中断。

### 16.4 Dockerfile 要点

```text
多阶段构建：deps → builder → runner
builder 阶段执行 pnpm install --frozen-lockfile、prisma generate、next build、tsc
runner 阶段只 COPY 产物 + node_modules（生产依赖），以非 root 用户运行
基础镜像 node:22-slim（有 arm64 变体）；argon2 等原生模块需在 builder 内编译

```

## 18. 成本控制

### 18.1 X API 定价（本次核实，来源：docs.x.com/x-api/getting-started/pricing）

计费模式：**信用点预购 + 按用量扣费**，无订阅费、无最低消费、无合约。

读取类（按**响应中返回的资源数**计费）：

| 资源 | 标准单价 |
|---|---|
| Posts: Read | **$0.005 / 资源** |
| User: Read | $0.010 / 资源 |
| List: Read | $0.005 / 资源 |
| Like / Mute / Block: Read | $0.001 / 资源 |

写入类（按请求计费，**本项目不使用**）：

| 操作 | 单价 |
|---|---|
| Post: Create | $0.015 / 请求 |
| Post: Create (**with URL**) | **$0.200 / 请求** |
| Post: Create (summoned) | $0.010 / 请求 |

**Owned Reads 优惠**：当请求由你自己的 Developer App 发起、`{id}` 匹配认证用户、且该用户是 App Owner 时，以下端点按 **$0.001 / 资源** 计费：

```text
GET /2/users/{id}/tweets          ← 本项目核心端点
GET /2/users/{id}/mentions
GET /2/users/{id}/liked_tweets
GET /2/users/{id}/bookmarks
GET /2/users/{id}/followers | following | blocking | muting
GET /2/users/{id}/owned_lists | followed_lists | list_memberships | pinned_lists
```

**上限**：pay-per-usage 计划每账期最多 **300 万次 Post reads**，超出需 Enterprise。

### 18.2 本项目的真实成本模型

关键理解：**计费单位是「响应中返回的资源数」，不是「请求次数」，也不是「你发的帖子数」。**

```text
每 30 秒轮询一次 = 2,880 次请求/天 = 86,400 次请求/月

若 since_id 之后没有新帖 → 响应返回 0 个资源 → 该次请求 $0
若有 1 条新帖         → 返回 1 个资源     → $0.001
```

所以高频轮询本身**几乎不产生费用**，费用只与实际读取到的帖子数相关。

**月度估算**（假设一个月发 300 条 X，全部为原创且都命中同步规则）：

```text
理想情况（24h 去重全部生效，每条帖子只被计费一次）：
    300 × $0.001 = $0.30

保守情况（跨 UTC 日重复读取、去重未生效）：
    最坏 300 × $0.005 = $1.50（若 App Owner 条件不满足，标准价）
```

**⚠️ 待验证项**（官方定价页未明确，需实测）：

1. 空响应（`data` 为空数组）是否绝对不计费。
2. `expansions` 展开的 media 对象是否单独计为资源。
3. `pagination_token` 翻页时，已计费过的帖子在**同一** UTC 日内是否稳定去重。

验证方法：开启 Usage endpoint 采集，跑 24 小时后对比「实际读取帖子数」与「Usage 报告的消耗数」。

### 18.3 去重是 soft guarantee

官方原文：资源在**同一 UTC 24 小时窗口**内去重，重复请求同一资源不重复计费；窗口在 UTC 午夜重置。但官方明确称其为 **soft guarantee**——绝大多数情况生效，服务中断等边界情况可能不去重。

**因此程序自身必须做去重，不能依赖 X 的计费去重**：

```text
since_id                          从源头避免重复请求已见过的帖子
x_posts.x_post_id 唯一索引         INSERT ON CONFLICT DO NOTHING
sync_job 幂等键                    防止重复发布
Redis 短期缓存 last_tweet_id       减少无意义的数据库往返
```

### 18.4 平台侧成本保护

X Developer Console 提供：

```text
Spending Limit    设置每账期最高支出，达到后阻止 API 请求
Auto-recharge     余额低于阈值自动充值（5 分钟内最多触发一次；余额 ≤ 0 时暂停）
Credit Balance    实时余额显示；余额可为负，为负时请求被阻止直到补足
Usage endpoint    GET https://api.x.com/2/usage/tweets → 每日 Post 消耗计数
```

**部署前必须做**：在 Developer Console 设置 Spending Limit（建议首期 $5），**关闭** Auto-recharge（避免程序 bug 造成意外扣费）。

### 18.5 系统内成本监控

```text
每次 X 请求后：记录返回的资源数到 api_usage_logs
    字段：account_id, endpoint, resources_returned, estimated_cost_usd, at
每日汇总：按 UTC 日聚合，Dashboard 显示本月累计与预估
定时任务：每日调用 Usage endpoint，与本地估算对账，偏差 > 20% 时告警
余额告警：若可通过接口获取信用余额，低于 $1 时后台红色横幅
```

### 18.6 Binance 侧成本

Binance Square OpenAPI 发帖**不收取 API 费用**，但有硬限额（100 帖/日、400 上传/日）。成本风险不是金钱，而是**限额耗尽导致同步中断**——因此 §11.2 的前置计数是必需的。

### 21.2 为什么保存 content_snapshot

X 原文、模板渲染结果、AI 改写结果、最终发布内容可能各不相同。必须**同时**保存：

```text
x_posts.text                X 原文（不可变）
sync_jobs.content_snapshot  最终发往 Binance 的正文
binance_posts.content_snapshot  实际发布成功时的正文快照
binance_posts.media_snapshot    实际使用的图片 URL 列表
```

这样才能事后回溯：`X 原文 → 模板/AI 结果 → 最终发布内容`，对排查「为什么发出去的内容和预期不一样」至关重要。

### 21.3 为什么 last_tweet_id 用字符串

X 的 Tweet ID 是 64 位 Snowflake，超出 JavaScript `Number.MAX_SAFE_INTEGER`（2^53）。必须用 `String` 或 `BigInt` 保存与比较。若用 `Int`/`bigint` 列则 Prisma 映射为 `BigInt`，比较逻辑需显式处理。**本项目统一用字符串存储 + 转 BigInt 比较**，并在 Zod schema 中校验格式为纯数字。

## 24. 第一阶段验收标准

必须全部通过：

```text
① 我发一条 X
        ↓ 30 秒以内发现
        ↓ 数据库记录（x_posts 唯一）
        ↓ 进入 Queue
        ↓ Binance 自动发布成功

② 服务器重启
        → 不重复发布
        → 不丢失中断期间的帖子

③ Binance 断网
        → 任务保留在队列
        → 网络恢复后继续处理

④ Binance 请求超时 / 504
        → 状态变为 UNCERTAIN
        → 绝不自动重复发布
        → 后台出现待确认提示

⑤ X API 返回 429
        → 读取 reset 头并自动退避
        → 不产生请求风暴
        → 恢复后自动继续

⑥ 首次连接账号
        → 只设置 baseline
        → 历史帖子一条都没有被同步到 Binance

⑦ 密钥安全
        → 数据库查询看不到任何明文 Token / Key
        → 日志 grep 不到任何敏感字段
        → 后台 API 响应不含完整密钥
```

## 27. 术语表

| 术语 | 含义 |
|---|---|
| Owned Reads | X API 优惠计费：读自己的数据时 $0.001/资源，需 App Owner = 认证用户 |

## 28. 核心原则（四句话）

> **TypeScript 负责整个应用。**
>
> **X 官方 API 负责发现内容。**
>
> **PostgreSQL 负责记忆和去重。**
>
> **Redis + Worker 负责可靠发布。**

再加上本次修订补上的第五句：

> **结果未知时，宁可停下等人，也不自动重发。**

这样做出来的不是一个「脚本」，而是一个可以长期无人值守运行的服务器程序。
